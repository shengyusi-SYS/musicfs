# MusicFS 缓存优化：决定与重开条件

当前直接 DAV 共享读取方案已随 dev.11 交付。本文只保留取舍与后续候选，现行默认值、所有权及流程见[缓存策略](../architecture/cache-policy.md)和[共享读取设计](../architecture/shared-read-cache.md)；版本证据见[缓存消费](../verification/cache-consumption-2026-10-21.md)与[共享读取验证](../verification/shared-read-cache.md)。

## 已确定的方案

| 用户问题 | 选择 | 保留的边界 |
|---|---|---|
| 短期重进目录重新枚举 | 挂载目录缓存可配置；本机成功发布后定向失效 | 目录缓存不缓存音频正文，远程挂载按自身策略更新 |
| 文件管理器读少量标签却放大下载 | 较小内存缓冲、适当起步块和递增连续读取 | 缩小预读需同时核对播放等待及 SDK/CDN 请求数 |
| App 挂载重复读取仍回源 | 复用 rclone 原生 full 稀疏缓存，管理实际状态、容量和清理 | 仅缓存已取得区段，首次/新范围/淘汰后仍取源 |
| 直接 DAV 客户端不缓存正文 | 桌面复用 rclone 服务端 VFS，共享最终表示片段 | 对外仍由原 DAV 处理认证、条件与范围；Worker 保持流式 |
| 两层缓存重复写盘 | App 本机挂载走内部直读，使用自身 VFS；直接 DAV 使用共享 VFS | 两个入口容量独立，用户总磁盘预算需合计 |
| 稳定资料反复重建 | 插件配置资料保留期，选定目录复用既有定时刷新 | 临时 URL/授权期限不随资料缓存延长，旧表示字节不随 TTL 改变 |

## 候选比较与停止理由

以下是选择记录，替代方案不叠加估算，也不继续作为待办。

| 方向 | 决定 | ROI 与原因 |
|---|---|---|
| rclone 服务端 VFS | **已采用** | 复用已有运行时的范围存储、重叠复用及容量回收；只接入身份、回环路径和生命周期 |
| 仅缓存完整短 Range 响应 | 不采用 | FFprobe 的开放 GET 与提前取消不符合这个前提；短 Range 命中不能覆盖主要消费模式 |
| 流式首尾窗口 | 不另做 | 可覆盖部分扫库，但仍需部分提交、拼接与回收；现有 VFS 已覆盖更完整的读取需求 |
| 项目自制持久分块引擎 | 不采用 | 只有现有 VFS 出现具体无法适配的合同缺口时才重估；无需并行维护另一套范围协调 |
| 完整读完才缓存整曲 | 不作为扫描方案 | 提前取消的扫描不能形成完整对象，不应为填缓存继续下载整曲 |
| 单纯延长 HTTP 新鲜期 | 不作为正文缓存替代 | 依赖客户端行为，且可能推迟目录更新；准确条件响应继续保留 |
| Worker 音频块缓存 | 延后 | 需独立评估边缘命中、调用及 CPU；桌面磁盘收益不能外推，不默认新增云存储 |
| 全库预热、跨账号去重、高并发缓存平台 | 不进入当前范围 | 不对应当前单用户按需需求，会增加平台访问和维护成本 |

原先“短 Range 方案不合适”只排除了该方案；它不能推导出所有流式或原生 VFS 路线 ROI 都低。服务端复用的垂直验证改变了选择，现行结论以已采用方案为准。旧估算和中间计划可从 Git 追溯，不与当前决定并列。

## 剩余风险与重开条件

| 观察到什么再重开 | 优先动作 | 成本与 ROI 判断 |
|---|---|---|
| 热扫描仍有明显回源 | 区分新范围、容量淘汰、版本失效与未启用；核对实际状态和常用工作集 | 配置或小范围定位优先，不先重写缓存 |
| 真实播放卡顿或 SDK 请求增加 | 在现有递增读取上比较请求、字节和等待 | 有限参数/接线改动优先；无净收益则停止 |
| Worker 同区域重复读取确有主要成本 | 先做一个能判定收益的有界样本，再估实现 | 当前收益未知，不保留过期的产品化工期承诺 |
| VFS 无法满足已确认的最终表示或生命周期合同 | 记录具体缺口，比较修正 Adapter 与替代实现 | 仅此时重估窗口或分块引擎，不同时建设两条路线 |

缓存容量按实际常用工作集评估。已有 Windows 单曲读取范围的外推只能作为容量模型，不能宣称真实全库占用或卡顿根因已测定。管理状态是原生取样，可能滞后；一次命中也不证明整曲已缓存。

依赖调查中 HTTP 缓存策略、字节存储和范围协调的能力边界见[主源记录](../research/shared-read-cache-options.md)。该调查保留当时日期，当前实现不再由其中的旧“尚未实现”措辞决定。
