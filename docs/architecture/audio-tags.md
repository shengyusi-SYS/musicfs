# 可选的音频补标签设计

日期：2026-10-21。来源插件可自行补标签，也可选用共用工具或完全透传；这项职责已经确认。具体格式接线尚未实现，实验及范围见[验证记录](../verification/metadata-tagging-feasibility.md)。

## 核心只接收最终文件

公开 `SourcePlugin` 的 `list/stat/open` 已能表达三种实现，不增加强制的 `tag` 方法、音乐字段、标签能力开关或新的插件类别：

| 插件实现 | 交付的内容 | 核心的处理 |
|---|---|---|
| 透传 | 上游原文件，可能已有完整标签，也可能没有 | 按通用文件合同读取 |
| 自带补标签 | 插件自己的代码、第三方库或来源已生成的带标签文件 | 按同一合同读取，不再次补写 |
| 选用共用工具 | 插件取得音乐资料，调用可选工具形成带标签文件 | 按同一合同读取，不依赖工具实现 |

补标签不是所有来源的必选能力。上游不提供的格式和资料不由核心补造；共用工具未支持的格式，也不禁止其他插件输出。QQ、网易云按其实际来源能力补全本次目标资料，不把示例格式集合变成核心白名单。

三种实现的 `Entry.info`、`stat` 和 `open` 都描述同一份最终字节：准确大小、媒体类型、内容身份及实际范围。标签改变也改变文件内容身份；临时 URL 更新而字节未变，不构成新文件。不能先公布原大小，再在首次读取时悄悄增加封面或歌词。这是已有文件合同，不是新增音乐协议。

## 模块与依赖方向

| Module | 隐藏的实现责任 | 对调用者的 Interface |
|---|---|---|
| 来源插件 | 平台请求、字段映射、原标签处理、资料缺失与更新策略、音质版本、资料准备与复用 | 既有 `SourcePlugin` 文件操作 |
| 可选音频工具 | 库的格式差异、标签序列化、文件区段组合、最终描述与范围映射 | 准备最终表示，再按该表示读取；不知道账号、歌单和平台接口 |
| `library` / DAV / `mounts` | 快照、路径、HTTP 属性和实际文件访问 | 既有通用文件 Interface |

工具是插件构建时选用并打包的依赖，不由核心全局注入。插件可替换它，无需修改核心或重新编译 MusicFS。工具只引用公开类型和所需格式库，不导入 `core`、DAV、宿主入口或数据库。结构图见[可选标签处理](diagrams.md#可选标签处理设计)。

两个示例形成真实复用时，可集中为一个 `packages/audio-tags/` Module；该包目前尚不存在。不预先创建空包、格式注册中心或多层透传包装。`plugin-api` 继续作为公开类型合同；音频工具独立版本、按需采用，不成为宿主必选能力。

工具的最小 Interface 围绕最终表示：

1. 准备：接受插件映射后的资料和可取消的原文件范围读取能力，返回最终描述与可重建的表示计划；隐藏必要头尾探测和标签编码。
2. 读取：接受同一计划及最终范围，组合标签与原音频区段，返回实际范围及可取消流。

这里是职责设计，不是已经发布的函数或 DTO。现成库负责标签编码；少量区段/偏移适配集中在工具内部。来源语义、资料缓存和请求预算不塞进格式编码器。整文件 buffer 实验通过，也不等于已适合作为 Worker 默认路径。

## 准备、缓存与身份

需要补标签的示例插件优先在现有分页准备中复用详情字段，补取缺少的封面、歌词，再公布最终 `info`。封面按专辑、歌词按歌曲复用，不按歌单位置和每个音质重复取。首次冷准备仍有真实来源请求成本，先用小目录核算，不刷新大账号。

现有 PROPFIND `allprop` 描述该层文件，缺少 `info` 就调用 `stat`。把全部资料获取推迟到 `stat` 只是把成本挪到列目录，不能宣称只播放一首才准备一首。透传或上游已提供最终描述的插件不走这套准备。

最终 `FileInfo` 继续随既有快照保存，不另建平行文件目录。表示身份由实际音频身份和最终标签内容/编码方案共同确定；歌曲身份与目录出现身份分开。缓存引用和最终表示必须对应；刷新产生新表示，不能让旧引用悄悄读取新字节。

需要跨调用保存小资料时，再在既有 SQLite/D1 上补明确所有者的通用插件缓存；当前 `Context` **尚未提供**该能力。它不是所有插件必须使用的设施；不把封面、歌词塞进认证 `privateState`，不默认增加 R2、整曲缓存或新调度器。

## 格式与实施

本轮只取现有来源并集：MP3、FLAC、M4A，以及有上游 SDK 实现、尚缺真实来源样本的 QQ APE。网易云不增加 APE；WAV、OGG、Opus、DSD 等不因库支持而加入本轮。这不限制第三方插件输出其他格式；音质档位与实际容器分别判断。

优先考察可选依赖 `node-taglib-sharp`，实际结果见[验证记录](../verification/metadata-tagging-feasibility.md)。MP3/FLAC 先闭合小标签与原区段组合；APE 依据尾标签验证；M4A 需处理容器偏移，不能套用 MP3 前缀。成本不同就在工具内选择已验证实现，不升级成全局架构重写。

接线后只做小目录准备、代表文件资料读取、跨区段 Range 与音频一致性验收。歌词时间轴保存与播放器逐行滚动分别确认，不做平台压力测试或播放器矩阵。当前格式实验不代表产品已经支持自动补标签。
