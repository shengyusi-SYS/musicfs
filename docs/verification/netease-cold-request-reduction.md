# 网易云冷准备：SDK 批量与按需读取评估

日期：2026-10-21。实现提交：`4a44356`、`8119104`；候选网易云alpha.11，应用/API/schema仍为dev.5 / 0.1.7 / 9。当前未重新发布整个应用，也没有重复真实整库刷新。

本页保存 alpha.11 的调查时点；后续 alpha.12 已实现两阶段清单，真实冷清单与单文件、本地 Worker 及客户端结果见[当前验证](deferred-catalogue.md)。下文“下一步/仍需实现”是当时结论，不是当前待办。

## 为什么重开

[一次真实冷扫描](real-netease-cold-dev5.md)的4,159首耗时778.202秒。9,266次来源请求中，名单、详情和版本共78次；专辑、歌词、图片、音频结构准备共9,188次。管理接口很快并不代表首次目录可用很快。没有HTTP429，仍不能排除业务限流；本轮不通过加压猜测限流阈值。

## 真批量优先于 HTTP 打包

当前锁定SDK `NeteaseCloudMusicApi 4.32.0` 的 `song_detail` 调用v3端点，返回紧凑的 `al`，缺少专辑艺术家等资料。其通用 `api` 模块可以沿相同SDK选项、加密与现有Fetch Adapter调用 `/api/song/detail/`。现在每批最多100首，从 `artists/album/disc` 规范到插件内部格式；完整详情查询的私有标记避免来源确实缺字段时反复请求，缓存24小时且命中不续期。歌单中的基本资料不等于富详情，稀疏seed也会批量补齐；同一专辑的新歌单名称、封面引用优先。

有界真实验证：3首GET、3首SDK加密请求均返回所选ID；随后一次100首SDK加密请求完整返回100首，用时322ms。与既存专辑缓存比较，专辑艺术家名称100/100相同、发行时间98/100相同、专辑曲数85/100相同。不同接口/时点资料并非逐字段完全一致，采用详情自身返回的资料，缺少必要资料仍回补；不因“批量”而推断完整性或忽略错误。

SDK也有 `/api/batch`，但只是以路径为键聚合业务调用。歌词端点是同一路径加单个ID，重复键不能表达多首歌词。没有采用无证据的query后缀技巧，也没有为了合并本可删除的专辑查询接入第二条批处理路径。

## 同一资源少取一次

- **封面**：现有冷缓存1,762条对应1,640种图片资源路径；相同路径跨分片的缓存字节一致。alpha.11对已知p1—p4图片域按路径及参数共享，保留原访问URL，未知域使用完整URL。不能仅按专辑ID共享，不同封面路径仍分别读取。
- **MP3头尾**：来源原先通常读头、尾各一次。CDN有界探针确认一次多Range请求返回两段真实区间；外层错误标为audio/mpeg，正文却是标准multipart。私有Adapter只补取开头boundary，实际MIME交固定`@remix-run/multipart-parser 0.16.5`解析。它是跨Bun/Worker的现成解析器，不引入Remix应用框架。[维护方源码](https://github.com/remix-run/remix/tree/main/packages/multipart-parser)
- **正式reader验证**：一首真实完整MP3，一次原生定位、一次CDN请求，取得两个4KiB区间；大小、范围、内容身份全部相符，用时336ms。这只证明小范围合并可用，不是整库时间或完整解码验收。

可选音频工具新增兼容的 `ReadRange.readMany?`，MP3/APE准备才使用首尾窗口，重叠窗口合为一次单段读取；FLAC/M4A不添加无用尾部请求，实际open仍按用户所需区间流式读取。网易云提供该可选能力，QQ及第三方无需跟随；它不让核心认识CDN或音乐资料。不支持多Range的实际响应会取消并回原单段路径；真实版本/区段不一致仍失败，不靠重试替换内容。

以上按原样本推算，可省大部分1,675次专辑查询、约122次图片查询和约1,915次头尾查询，需扣除少量新增富详情批次和缺字段回补。**预计总请求可减少约四成，不等于整库耗时已降低四成。** 1,915次歌词仍是逐首来源工作。合并不是并发提速，也不能保证平台按较少的内部工作计费或限流。

## 按需准备与播放器扫描

当前仍是“该目录所有文件准备成功，再完整发布”，所以前三项并不解决首次使用被整库阻塞的结构问题。这是下一项高ROI工作，不收为完成。

建议的职责：插件先组织完整名单、音质筛选和轻量文件引用，音乐资料及最终表示由同一个单曲准备入口按需形成；library继续拥有完整集合与路径，协议层区分名字枚举和精确文件属性。不增加强制音乐接口，不创建第二套歌曲数据库或独立通用队列。

| 实际操作 | 必须满足的行为 |
|---|---|
| App浏览、DAV只请求名字 | 不触发所有歌曲的歌词、图片、音频布局读取 |
| 单首HEAD/GET | 只准备所需文件；HEAD与后续GET、Range指向同一永久计划 |
| 播放器逐首读取标签 | 按真正扫描的歌曲准备并复用；不准备未访问的其余文件 |
| rclone或播放器整层allprop | 准确大小必须可得；不能把等待悄悄移入一次超长同步请求 |
| 重启、刷新失败、来源换号 | 沿现有持久状态和来源代际处理；完整名单/旧可读文件保持明确语义 |

关键兼容事实：[rclone v1.75.2](https://raw.githubusercontent.com/rclone/rclone/v1.75.2/backend/webdav/api/types.go)将缺失DAV大小解为0，随后按已取得属性处理。因此“省略大小，首次GET补标签”不能直接作为默认挂载方案。固定标签预留空间则增加各格式布局、容量上限及传输代价，当前不采用。完整清单先可见、全属性的异步准备如何与现有持久刷新衔接，仍需实现与小范围客户端验证；不把仅App快列目录称作全量播放器扫描完成。

## 集成结果

71项相关测试、5,213断言通过，包含4,000首离线增删/到期场景、三种网易云格式、可选工具全部现有格式和QQ兼容回归；三套类型检查与226模块/883依赖方向检查通过。实际打包SDK的本地workerd/D1，24首相同规模冷准备来源请求由旧记录80降为55，最多37条SQL保持不变；热刷新仍为1页、24SQL、3次来源调用，最终音乐标签和尾部Range正确。这个受控24首样本所有歌曲共用专辑，不冒充真实账号分布或免费云端CPU验收。

最终生成的SDK包装另以3首真实歌曲确认，字符串ID数组完整返回3/3，用时59ms。插件包已生成alpha.11；现有本地实例没有再次更新/重刷，避免提前清掉真实验证留下的有效资料。整应用dev.5归档保持原身份。

本轮真实验证只用了少量详情与单曲范围请求，没有再次清空/扫描账号、部署云端或调用Windows宿主。匿名汇总见[数据](data/netease-cold-request-reduction-2026-10-21.json)。
