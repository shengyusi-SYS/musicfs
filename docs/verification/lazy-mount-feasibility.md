# 真正按需挂载：有界可行性验证

日期：2026-10-21。用户反馈 App 创建的 rclone/FUSE 磁盘直接进入网易云大目录仍卡住，必须先在管理页准备文件。用户明确选择优先验证真正按需，而不是仅给整目录准备增加进度提示。本轮不访问音乐平台、不部署云端、不调用 Windows 宿主。Windows 测试 VM 最初连接失败；用户随后要求重试并在 VM 内重连网络，SSH 恢复后完成下文限定验收。

**结论：保持现有 rclone、WebDAV 和准确文件合同，有一条可行路线：来源插件提前公布带合法预留空间的最终大小，打开/读取单曲时才生成其标签计划。** 网易云范围的MP3、FLAC、M4A均已通过Windows App/WinFsp及WSL正式App/FUSE小样本。APE另已通过WSL文件读取/解码试验，但自定义填充项会暴露额外附件，不作为同等成熟的默认方案，Windows及真实QQ来源仍未验。这些不是生产插件接线或资源管理器可见窗口验收，不能把原型结果写成 dev.6 已修复。

## 原因与方案比较

当前 rclone WebDAV `List` 一次要求整层属性；MusicFS allprop 需要最终补标签文件的准确大小。旧实现遇到延迟资料时返回 503 并启动整目录 file-info 任务。根目录只有子目录，所以 App 根目录探测成功不代表进入歌曲目录会顺畅。此前 rclone CLI 的准备后读取证据没有覆盖用户这条冷挂载旅程。

| 方向 | 本轮结果 | 判断 |
|---|---|---|
| App 自动整目录准备 | 可以改善提示，仍先处理整目录 | 不符合本次优先方向 |
| HTTP 后端 `--no-head` | 名称立即可见，但文件显示 0；同句柄跳读失败 | 不直接采用 |
| 修改 rclone/自行开发挂载实现 | 能调整属性取得时机，但未知可变长文件仍要定义大小语义 | 当前没有必要承担这条维护路线 |
| 来源插件提供预定大小的标签表示 | 音频合法 padding，准确大小与单曲延迟处理可兼得 | 已选择；dev.7接线及本地验证见上节 |
| 原音频及外置资料 | 原音频大小可直接用；播放器是否使用外置资料不同 | 用户效果不同，保留为取舍而非静默替代 |

### 为什么不能仅换 rclone 参数

固定版本 rclone v1.75.2 的 HTTP `no_head` 跳过逐文件 HEAD，将未知大小交给 VFS。[HTTP 后端源码](https://raw.githubusercontent.com/rclone/rclone/v1.75.2/backend/http/http.go)、[VFS 文件源码](https://raw.githubusercontent.com/rclone/rclone/v1.75.2/vfs/file.go)。

单次原生 Linux FUSE、六个离线 WAV：目录 2.4ms，仅一次目录 GET；全部 stat=0。open 不读时 fstat/SEEK_END 仍为 0。首次顺序读取 64 字节正确；属性缓存到期后该文件显示 524,332 字节，但**同一打开句柄尾部 pread 返回 0**，没有 Range 请求。关闭重开后可读尾部。冷文件 ffprobe 无时长、size=0，同源普通文件能正确报告时长。

读取句柄初始化把未知大小记为 0，首次 GET 更新后端对象而没有同步该句柄；非连续读取按旧大小提前 EOF。[读取句柄源码](https://raw.githubusercontent.com/rclone/rclone/v1.75.2/vfs/read.go)。Windows cmount 的目录枚举还填充每项 stat 信息，不能假定仅给名字即可。[cmount 源码](https://raw.githubusercontent.com/rclone/rclone/v1.75.2/cmd/cmount/fs.go)。当前 MusicFS 目录 GET 也不是 HTTP 后端所需的 HTML 名称列表。其他缓存选项没有被当作已验证的修复，不扩展无价值组合矩阵。

## 预定大小如何工作

平台批量响应已提供原音频精确大小 `N`。插件给其文件表示分配固定额外预算 `B`，目录立即声明**真实最终大小 `N+B`**。读取该首时，复用现有标签库与 prepare/open，取得歌词、封面、原文件布局并生成标签；剩余部分填为格式允许的 padding。移除旧标签释放的字节也可供新标签使用，不需要假设上游没有原标签。

```mermaid
flowchart TD
  Catalogue[完整清单及原文件准确大小 N] --> Describe[插件分配表示版本和预算 B]
  Describe --> Listing[普通 DAV allprop 返回准确 N+B]
  Listing --> Disk[rclone 直接列目录和文件属性]
  Disk --> Read[播放器打开或读取某一首]
  Read --> Resolve[仅该首取得资料并生成不可变计划]
  Resolve --> Padding[格式标签 + 合法 padding + 原音频区段]
  Padding --> Range[同一版本准确大小及 Range]
```

原型按此图调用既有 audio-tags prepare/open，格式序列化由 `node-taglib-sharp@6.0.3` 负责。MP3 在库输出后调整 ID3 长度及填充；FLAC/M4A 使用库公开的 PADDING/free box 工具，不增加新的标签库或重写音频编码。dev.7生产接线继续使用这一路线，并以紧凑生成区段替代原型的完整空白字节，现行流程见[架构图](../architecture/diagrams.md#可选标签处理设计)。

### 真实 MusicFS → DAV → rclone → FUSE

六个不可变离线 MP3，预算 64KiB；包含既有 ID3v2、ID3v1、封面、歌词和副标题，不是假音频。源 18,895 字节，导出每首 84,431 字节。

| 操作 | 实测 |
|---|---|
| 冷目录 readdir 加六个 stat | **26.6ms**，全部大小准确 |
| 列目录期间资料准备/源 Range/封面/歌词 | **全部 0** |
| open 不读 | 大小准确，没有准备歌曲 |
| 首次读 64 字节 | 14.6ms，只准备选中的一首 |
| 同句柄尾读、反向跳读、重读 | 均正确，与完整表示切片相同 |
| 完整读取和 ffprobe | 字节、大小、1秒时长、中文标题/歌手/专辑正确 |
| 其余五首 | 完全没有准备 |

实验正常卸载。这里的 64KiB 仅用于小夹具；不能据此选择真实歌曲预算。耗时是离线 localhost 结果，不是大歌单、真实平台或 Windows Explorer 的性能承诺。rclone 可以预读被打开歌曲的数据；证明的是不因枚举而处理其他歌曲，不是禁止读取所选歌曲。

### Windows VM：实际 App/WinFsp 路径

用户在 VM 内重连网络后，同一 `192.0.2.74` SSH 恢复。只在这台已授权 Windows 11 VM 操作，复用已安装 WinFsp，未调用 Windows 宿主或修改网络、认证策略、注册表/证书。使用已有正式 dev.6 ZIP 的 `MusicFS.exe`（SHA256 `f29ef85c141c83e35abccefd3cbbdb05fa015024b4e1baf1519d972d7e0421a4`），独立临时数据目录。

App 正式 `POST /api/mounts` 创建远程来源挂载，自动分配 `Z:`，由随包 rclone v1.75.2/WinFsp cmount 执行。目标通过仅绑定 VM 回环的临时 SSH 反向转发，连接 WSL 的真实 Library/DAV 离线原型；它验证 Windows 消费端，没有将测试插件装入正式网易云实例。六文件采用 **1MiB** 预算，每首准确大小为1,067,471字节。

| 原生 Get-ChildItem 及每文件 Length | **30.3ms**，六项完整，全部大小准确；准备/源Range/封面/歌词均0 |

Windows 的打开阶段可能触发系统/客户端读请求，因此承诺应为“列目录不准备歌曲；打开/读取哪首只处理哪首”。不能把 Linux 的 open不读=零准备当成 Windows 的必要条件。没有定位这些额外读请求的具体系统组件，也不为消除它们改系统设置。

第一轮探针正是在这个不合适的断言处停止，此外 PowerShell 空数组包装使“挂载记录移除”的脚本判断误报；修正探针后，从新冷夹具完成文件系统链路。原生音乐资料查询的首版 COM 方法/签名亦不适用，随后只检查已选中的热文件，改用 `FolderItem.ExtendedProperty` 和 WMP `getItemInfo` 后取得上述结果，没有再跑冷扫库。第一轮原始回执与这些工具修正均保留，不将它们记为产品修复。

WMP对原始离线源的时长估计为1.078s，挂载表示为1.07s；记录实际差异，不宣称与FFmpeg的1秒媒体时长完全一致。Windows Shell 读到两位歌手，而WMP的Author接口仅返回第一位，不能保证所有消费端展示相同。

这是六首合成音的原生文件系统与字段验证，没有打开资源管理器可见窗口、实播声音、展示封面或滚动歌词，不代表4,000首真实平台时延或全部格式Windows验收。[Windows原始汇总](data/lazy-mount-windows-2026-10-21.json)

### FLAC、M4A：后续Windows格式验证

用户追问其他格式后，复用同一VM、现有WinFsp、正式dev.6 App挂载API和隔离Library/DAV原型。每格式一个有效合成源，目录各列两个文件引用，**仅打开每格式的第一个**。没有重测MP3、访问平台、安装播放器/系统依赖或下载源码/音频；结束后正常卸载、退出并删除本轮VM临时目录，关闭SSH转发与WSL服务。

## 格式与实际预算

| 格式 | 一个有效样本的结果 | 需要保留的边界 |
|---|---|---|
| MP3 | 合法 ID3 padding；标签/三路歌词/封面、原音频字节、完整和 seek PCM 相同 | ID3 长度有限；解析器对完整日期、多位专辑艺术家仍有既有差异 |
| FLAC | 合法 PADDING；Windows挂载/Range及字段、标签、音频字节、完整/seek PCM通过 | 单块长度为24bit；填充块头也需空间，实际布局需处理边界 |
| M4A | 沿现有旧 moov→free、尾部新 moov，再补 free；Windows挂载/Range及字段、mdat位置、音频字节和完整/seek PCM通过 | 预算包含完整新 moov，长曲 sample table 也占预算；不为统一强制套用 |

MP3/FLAC/M4A 样本准备读取 6,607/4,096/1,002 字节；原标签或 moov 较大时会更多，这不是读取上限。网易云仍只覆盖这三种上游格式；QQ APE的额外WSL试验及限制单独记录，不扩大为真实来源/全部播放器通过。

另对**已有磁盘缓存**做一次只读聚合，无新平台请求：1,915份历史计划（MP3 1,914，M4A 1），补标签后增加字节的中位数136,275、95分位519,441、最大671,235。

| 每曲额外预算 | 缓存样本可容纳 | 超预算 |
|---|---:|---:|
| 64KiB | 460 | 1,455 |
| 256KiB | 1,342 | 573 |
| 512KiB | 1,821 | 94 |
| 1MiB | 1,915 | 0 |

**1MiB 是有现有使用数据支持的候选，不是任意歌曲都够的保证。** 未打开文件不需要存储这一份空白；完整下载/缓存则真实多出1MiB/首，本账号1,915文件约1.87GiB。支持 Range 的解析器可跳过 padding，顺序读取或读取整个标签的客户端可能传输它。播放器如果主动扫每首标签，就会触发每首准备；这与只枚举目录不同。

## 哪些限制不能靠小补丁消除

| 类型 | 已知事实与影响 | 合理取舍 |
|---|---|---|
| 准确大小与无限资料的矛盾 | 资料尚未知、预算有限，却要求任意封面/歌词都能放下，无法同时保证。当前只证明1915份已有样本适合1MiB，不是无上限保证 | 选择有限预算，超出时该首单独准备/更新表示；或改变资料范围，不能静默截断或临时增长同一文件版本 |
| 真实填充有导出成本 | N+B是真实含空白的文件。生成式区段能省宿主存储和内存，不能让完整复制的输出少B字节 | 接受每首额外大小；Range读取可跳过，不承诺所有播放器都跳过。减小预算会增加超出样本，已有统计可直接比较 |
| 真正扫库仍要逐首资料 | 播放器主动打开全部文件时，就实际请求了全部文件标签。延迟准备只能避免没有使用的歌曲工作，不能把完整入库变成仅列名称 | 缓存、共享封面、已有真批量继续减法；来源没有的歌词真批量不能靠增加并发变出来，受来源响应和限流约束 |
| 播放器展示归消费端 | 已观察到WMP歌词为空、M4A Shell只返回第一位歌手，MP3日期/艺术家及估计时长也有差异 | 文件保留完整资料并公布消费端范围；伴随歌词等是不同交付方式，不把标签库替换视为所有播放器兼容保证 |
| M4A容器结构成本 | 当前不移动mdat，需完整读取并复制新moov；预算包含整块moov。普通单moov已验，moof/mvex等分片布局在现工具明确不支持 | 按格式使用既有路线，必要时该首精确准备；覆盖分片结构需要不同容器处理，不为上游未使用的布局新增框架 |
| APE的填充语义不同 | 自定义binary item虽能让WSL解码/seek正确，却被FFmpeg暴露为额外附件 | 现有变长精确准备可继续；固定预算路线暂不默认采用，也不据一个消费者推断格式不可行 |

生成式padding区段、持久首读版本冻结、单曲超预算衔接、网易云插件接线已在dev.7实现，是工程工作而非先天限制；本地D1单请求预算已有上文证据；免费云端CPU/实际长期存储、APE Windows及真实QQ样本仍没有对应结论。它们不需要新建音乐核心领域、重写rclone或保存整曲。

## 原型阶段的接入设计（dev.7已落实）

1. **职责不变。** 来源插件拥有预算/文件表示/资料快照，audio-tags 处理格式及区段；核心仍只认识准确 FileInfo。优先网易云 MP3，再分别评估 FLAC、M4A。不是所有第三方插件都必须补标签，也不新增全局音质或音乐资料系统。
2. **填充按需生成。** 不把1MiB空白编码为 base64 存在每曲计划中。原型这样做产生1,400,448字节前缀，超过现有1MiB JSON单值合同；生产应使用紧凑的填充区段，维持流式及范围读取，不存整曲、不增加云存储。
3. **版本与字节同时稳定。** 目录期分配明确的表示版本，首次解析后以该版本冻结资料和计划。当前 plan digest 依赖最终字节，不能仅更换 size 就沿用它；辅助资料TTL更新、并发首读及缓存清理要沿同一版本责任处理，不能同 contentId/ETag 返回不同字节。优先小范围的持久首写确定语义，不造第二套任务系统。
4. **超预算是产品取舍。** 不能静默截断歌词/降封面、临时增长同一表示或报原文件大小。可以对该首单独准备并更新表示版本后重新枚举，或明确采用资料范围不同的方式；其用户体验要先说明。实验已确认大歌词超1MiB时明确拒绝，没有伪造成功。
5. **最小后续验收。** 原型的Windows App/WinFsp读取路径已由上节确认；生产接线后只补本机来源入口的一次冷清单/单首读取，复用已有准确大小、同句柄seek与未选歌曲零准备证据。无需重刷/补全真实整库、压力测试或再部署付费云端。

上述设计来自“先验证可行性”阶段，dev.7接线结果见本文首部；不修改dev.6发行包，也不将新版本的本地回归改记为Windows生产来源通过。候选和当前出口记录在[PERF21](../../outputs/musicfs-implementation-plan.md)。

## 原始证据与复现

[匿名汇总](data/lazy-mount-feasibility-2026-10-21.json)包含两个实际 FUSE 结果、格式/PCM检查和既有缓存预算统计。实验脚本留在本机忽略目录，不进入发行物：

- `.musicfs/lazy-mount-evaluation/wsl-formats-server.ts` 与 `wsl-formats/probe.py`：四格式真实Linux发行程序/App挂载入口；先启动隔离服务再运行Python探针，正常结束后关闭服务。APE源只使用上述固定hash的官方小样本，不下载仓库。
