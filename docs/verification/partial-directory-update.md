# 少量增删后的索引与缓存

2026-10-23，基于dev.21源码续接。目标是减少未变化歌曲的额外工作，不改变已接受的序号命名，也不增加平台请求。

## 结论与选择

变化目录仍在下一次访问时重建一次内存名称索引；它与标签准备、音频下载、客户端入库分别存在。无变化刷新继续复用旧内容版本。此次只修改原有LRU和直接DAV的原生通知参数，没有引入增量索引、文件时间表或数据库迁移。

| 方向 | 决定 / 工作量 | 收益与风险 |
|---|---|---|
| 及时移除同目录旧索引 | 已修正，局部小改 | 高ROI：新版本不再和旧版本共同占预算，避免挤掉其他目录；在途调用仍可使用自己持有的旧对象 |
| 共享音频桶登记新键 | 已修正，一处参数调整 | 固定桶内只有不可变文件，改用原生file通知，只使父清单过期；保留既有节点，不预热或清字节 |
| App任意目录改用浅失效 | 不推广 | 含子目录时，同名路径可能已换目标；盲目保留节点会留下旧内容。保持现有按变化目录递归forget，不新建目录差异跟踪 |
| 完整增量路径索引、跨版本逐文件ETag缓存 | 暂不实施，预计1—3日并增加维护复杂度 | 当前样本本机索引计算约11—13ms、全量描述约8—16ms；不足以支持新增另一套索引或内容键缓存，且命名碰撞仍需看完整集合 |
| 第三方插件缺少文件时间时逐文件持久化 | 暂不实施，预计0.5—1日且涉及存储升级 | 目录实际变化仍会推进缺省文件时间；网易云/QQ已有稳定文件时间。先在作者说明明确合同，不用假日期隐藏更新 |
| 取消序号或提供新稳定路径模式 | 保留现合同 | 会迁移展示路径及客户端索引；这是独立的命名选择，不能冒充本轮缓存修复 |

## 有界证据

`tests/library-views.test.ts`先复现：缓存只能保留两个目录时，A、B、再次访问A、发布A新版本，会因A旧版本仍占位而挤掉B。修正后B继续返回原对象，无第二次快照读取；并保留取消、发布切换、无变化刷新和估算容量边界。

一次4,000项SQLite/library离线样本采用桌面32MiB预算、原生SHA-256、650字节引用及稳定文件名/修改时间。新增一项后的4,000项原文件、删除一项后的3,999项原文件，其ETag与时间全部相同，未触发插件stat/open。索引重建分别约10.98/12.86ms，完整描述约16.13/7.50ms；哈希仍逐个重算。此处是合成数据的本机阶段成本，**不是实际音乐平台、Windows GUI或免费Worker计时**。[原始计数](data/published-partial-update-2026-10-23.json)

`bun run scripts/probe-directory-invalidation.ts`用随包rclone1.75.2、正式MusicFS DAV和回环小文件核对原生file通知：通知时0次来源请求；变化目录清单重读1次，已缓存子目录和无关目录不重读；相同范围0次来源open，内容和mtime真正变化后取得新字节。这个证据验证原生通知语义；生产只将其用于结构固定的共享音频桶，不将其推广成App任意目录的承诺。[原始结果](data/directory-invalidation-2026-10-23.json)

网易云既有小样本扩展了删除：无变化、插入、换序和删除后，存续歌曲继续使用原fileRef及info，标签、封面和音频Range均0次请求。文件名仍按序号变化。[插件回归](../../tests/netease-reserved.test.ts)

## 缓存影响范围

App原生VFS按路径与文件属性复用片段：未改名且大小、mtime不变的文件不因索引重建而被清空。直接桌面DAV的共享键不含展示路径，同一来源代际、引用和最终表示仍可命中。网易云前部增删导致的序号改名，仍可能让App及播放器自己的按路径缓存未命中；Worker继续流式读取，其他DAV客户端按自身策略缓存。资料过期、主动更新音乐资料、换号与插件升级沿原规则，不承诺跨这些变化复用。
