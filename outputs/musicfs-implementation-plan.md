# MusicFS 实施与交付计划

当前已交付 Windows dev.11 及对应源码；其他目标按各自已生成版本使用，不能把 Windows 更新当作 Worker 或全部桌面目标已升级。产物身份与升级步骤只在[发行页](../docs/release.md)维护。

性能主线按[Codex 完成标准](../docs/codex-goal.md)执行。上一轮已识别的路径已交付；本轮六领域独立评估和主代理复核又发现局部优化候选，详见[场景复评与ROI](musicfs-performance-review.md)。用户已授权按 O2 → O1 → O3 实施，不自动恢复历史验证矩阵。工程经验见[可复用结论](../docs/engineering-lessons.md)，产品范围仍以[统一需求](musicfs-requirements-and-technical-design.md)为准。

## 应用场景持续优化

用户现已授权持续推进至没有足够高ROI方向，目标工具已新建为active。按本地播放器、直接DAV、不同刮削、下载复制/同步等[应用场景](../docs/codex-goal.md#实际应用场景)重新评估；O4—O10也可以在该标准下重新选择，不因旧候选未实施就全部照做。

S1已修正未准备文件的表示稳定性，S2已接通按Range恢复共享图片；两者保留资料期限、旧表示和公共合同，证据见[局部核对](../docs/verification/performance-local-2026-10-22.md)。O9缓存关闭时的退出计数已完成模块修正，待主线程集成；来源定位正在比较直接复用现有有效播放版本缓存。候选依据与停止条件见[应用场景续评](musicfs-performance-review.md#应用场景续评)。路径命名保持当前顺序合同，旁置文件和新导出系统不预设为需求。

## 本轮复评与建议顺序

O2、O1、O3 已按顺序完成，分别提交：

| 项目 | 当前结果 |
|---|---|
| O2 挂载状态 | 无变化不写盘；稳定查询15秒，操作后立即刷新。原生挂载消失仍保存真实状态 |
| O1 路径索引 | 不附带原始快照；桌面32MiB、Worker8MiB估算预算，两个各6,000项的目录轮换可复用 |
| O3 单曲资料 | 有界样本支持实施；空余两个名额内重叠歌词/封面，多曲批量和Worker预算路径保持原节奏。独立示例插件alpha.16已构建 |

设计及必要回归见[局部性能核对](../docs/verification/performance-local-2026-10-22.md)。桌面发行包仍为dev.11，未重打或部署。O4—O10及停止条件只在复评报告维护，不自动全部实施；需要真实反馈改变优先级时再选择。

大目录保留的原始离线检查：合成4,000项仍命中，6,000项超过原8MiB预算后重建；新桌面预算的定向测试覆盖两个6,000项视图轮换。它们支持预算选择，不证明用户4,000首卡顿的实际根因，也不是GUI耗时或堆内存测量。

## 当前状态与下一出口

| 工作包 | 结果与设计入口 | 证据 |
|---|---|---|
| 目录与文件热路径 | 发布视图索引、准确描述/ETag 复用、SQL 去重索引、等价配置不失效、后台步间让步 | [性能设计](../docs/architecture/refresh-performance.md)及其历史计数链接 |
| 来源请求减法 | 网易云富详情/播放版本批量、名单复用、封面共享及可选头尾多 Range；QQ 热计划/路由复用 | [冷准备调查](../docs/verification/netease-cold-request-reduction.md) |
| 冷目录按需读取 | 网易云 MP3/FLAC/M4A 准确预留表示；目录和 HEAD 不做逐曲标签准备，GET 仅准备所读文件 | [设计](../docs/architecture/audio-tags.md)、[可行性与限制](../docs/verification/lazy-mount-feasibility.md) |
| 分层缓存与更新 | 挂载目录 TTL、插件资料期限、选定目录周期更新；共用持久刷新与旧快照 | [缓存策略](../docs/architecture/cache-policy.md) |
| App 与直接 DAV 读取复用 | 原生稀疏缓存、适度递增读取、实际状态/清理；本机挂载避免同次双层落盘 | [缓存决定](musicfs-cache-optimization-plan.md)、[共享读取验证](../docs/verification/shared-read-cache.md) |

以上证明对应路径已实现并有范围明确的证据，不承诺真实整库扫描固定秒数、所有播放器行为相同或免费云端资源已通过。

## ROI台账与执行次序

已完成项不再反复排成下一步；新候选见上节。下表保留上一轮未选方向及其重开依据，新证据改变优先级时以复评报告为准。

| 候选 | 当前决定 | 重开所需证据 |
|---|---|---|
| 网易云跨 open 地址复用 | 延后；保留原内容核对 | 能保留同表示验证且实际减少来源请求的方案 |
| 不变目录直接复用快照指针 | 延后；先沿用已优化分页/SQL | 正常使用确有频繁短时重刷，且成本仍占主要等待 |
| 跨插件升级保留资料/计划 | 延后；不建全局兼容迁移框架 | 升级冷重建成为主要瓶颈，且作者可声明兼容范围 |
| 改掉序号文件名 | 保留当前顺序合同 | 明确的路径稳定性需求与可接受迁移方案 |
| QQ 大封面存储 codec | 延后；热路径已避免大计划反复读取 | 真实容量或冷计划读写成为主要瓶颈 |
| 替换 XML 库或缓存整份 XML | 保留现有依赖 | 描述优化后 XML 仍造成实际可见等待或资源超额 |
| 进一步增大来源批量 | 保持已验证默认，非精确上限声明 | 上游能力/完整性有新证据；不反复探测阈值或加并发 |
| 更复杂的正文缓存或预读调参 | 当前停止 | 按[缓存重开条件](musicfs-cache-optimization-plan.md#剩余风险与重开条件)出现具体缺口 |
| 原生系统全矩阵、免费云端资源与自然续期 | 保留未验范围，不自动恢复 | 用户明确安排，或新变更确实依赖该证据 |

## 后续执行

1. 新反馈先分清清单刷新、文件属性、标签准备、播放器扫描及音频下载；复用现有匿名计数和目标版本证据。
2. 高 ROI 且有依据的问题进入原所有者模块；方案未知时先做一个有停止条件的样本，避免同时建设多个替代机制。
3. 按行为分配实现与集成，公共合同和依赖统一协调；完成一组受影响改动后再构建所需目标。
4. 本轮按已授权顺序实现并做定向离线核对，不请求平台、不部署、不覆盖现有归档。按行为提交，阶段交付仍保存到 `dist/releases/<版本号>/`。
