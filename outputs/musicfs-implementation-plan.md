# MusicFS 实施与交付计划

日期：2026-10-20。需求依据：[统一需求与技术方案](musicfs-requirements-and-technical-design.md)，架构决定见 [插件边界](../docs/adr/0001-installable-source-plugins.md) 和 [Worker 安装路线](../docs/adr/0002-worker-plugin-installation-by-deployment.md)。本计划安排实现顺序与验收，不增加产品范围。

持续执行范围及全部完成条件见 [Codex 主线目标](../docs/codex-goal.md)，实际实现、验证与外部条件缺口统一维护于[验收台账](../docs/verification.md)。目标覆盖 P0—P5 全部交付，各阶段结束后继续下一项未完成义务。

实现设计依据：[领域与模块设计](../docs/architecture/README.md)、[插件 Interface 草案](../docs/architecture/plugin-interface.md)、[图表](../docs/architecture/diagrams.md)。依赖接管范围见 [依赖选择](musicfs-simplification-and-dependencies.md)与[新增证据](research-architecture-dependencies.md)。基础实现与独立最小插件已经落地；接下来按实际缺口推进正式宿主和双来源交付。

主线是交付一套可安装数据源插件的只读音乐文件服务：用户用 WebUI 安装插件、配置和认证实例、组织目录，通过 WebDAV 播放，并在桌面一键挂载。网易云与 QQ 是完整可用的示例插件；桌面和 Worker 独立运行，来源规则与音质设置留在插件内。

## 交付顺序

阶段沿用统一方案 P0—P5，按端到端结果交错实现。最小 WebUI、API、存储和 DAV 必须提前参与首条可用链路，不等各自阶段全部完成后才联调。

| 阶段 | 主要交付 | 完成条件 |
|---|---|---|
| P0 关键验证 | 最小插件合同、两宿主原型、真实来源探测、音频/DAV 样本、挂载路线探测 | 关键假设取得实测证据或明确失败原因，形成支持矩阵；不存在未被承认的决定性障碍 |
| P1 第一条可用链路 | 一个真实示例插件、基础 WebUI、实例持久化、默认目录和 DAV 播放 | 从安装插件到认证、列目录、播放与拖动可重复完成，重启后有效配置保留 |
| P2 完整业务与第二示例 | 双示例的全部内容与音质规则、多实例、刷新/快照、插件生命周期及隔离存储 | 核心没有平台专用分支；示例内容完整、状态准确，更新失败与移除恢复符合合同 |
| P3 完整 WebUI | 插件/实例管理、声明式配置认证、目录树编辑、刷新与诊断、挂载管理 | 日常管理在浏览器完成；新插件不要求重编译前端，布局与来源刷新独立 |
| P4 双宿主产品化 | 桌面启动与随包 rclone、三端发行、Worker 插件自动部署与模板 | 从发行物或部署模板完成用户旅程，运行与更新状态可靠 |
| P5 发布验收 | 真实客户端/目标系统回归、资源表现、使用与插件作者文档、许可证 | 统一方案验收项逐项有证据，明确发布版本实际支持范围 |

P0 为后续每条路径解除相应风险，不设“等两平台所有接口和三端全部完成，才写第一条链路”的全局等待。Worker、另一平台或某目标系统验证等待期间，可继续已具备条件的本地链路；对应路径仍不得标为完成或在发布时省略。

## P0 当前应执行的工作

### 工程基础与最小插件

按架构设计建立一个应用工程、独立公开合同、三个核心领域 Module 与真实宿主 Adapter，配置严格 TypeScript、共用 Hono、React/Vite 和分宿主导入图；从首轮加入 dependency-cruiser 检查真实依赖。先安装本轮实际需要的成熟依赖，保留锁文件，避免一次搭建全部未来框架。

将已形成的试验版插件合同落实为可类型检查的包清单与公开类型，只承载身份、版本/宿主兼容、JSON Schema 配置与认证步骤、内容入口、目录、真实文件元数据及取消读取。复用 RJSF/Ajv 与 semver，归档库对 zip.js/fflate 同批验证后选一；验证作者生成的结构校验与双宿主加载。第三方内部校验实现保持可替换，实例上下文及持久状态由宿主明确管理，来源规则由插件解释。

用一个无账号、无歌单分类、无音质设置的最小音频来源验证：安装一个预构建包、创建两个实例、修改各自配置、列目录及读取已知字节。核心与前端不得为这个来源添加专用分支。原型产物应可复现；符合方向的代码保留进入应用，不维护第二套业务算法。

### 桌面与 Worker 两条插件安装路径

- 桌面：将核心编译为 Bun 可执行程序，收录 Vite 静态产物，加载真实用户目录中的外置插件并读写外部 SQLite。确认新插件无需重编译核心/前端，重启后实例状态保留。
- Worker：先复核普通 Worker 上传、版本部署、绑定保留与免费计划限制，再用最小插件验证模块组装和后台发布。验证新增、更新和移除后版本与实例状态一致，Secrets、D1 和页面资源保留，失败不破坏可用版本。该路线当前只有产品许可，没有技术通过证据。
- 两端：记录代码/配置变化与旧调用的关系，确保移除、换配置或换授权后的结果不能复活旧状态。加载策略和包格式用实测收敛，不把桌面动态加载方式直接推给 Worker。

Worker 验证须在真实部署中完成，桌面测试也须包含编译后的产物。账号或网络暂不可用时，先交付可复现的本地验证程序和精确待测步骤，继续其他工作；不能把未执行项写成已通过。

### 来源协议与音频读取

先选择一个示例来源跑通认证、一份完整集合和一份真实完整音频，同时尽早探测另一个来源在 Worker 中最不确定的认证/取流环节。现有报告提供 QQ `/serverless` 调查起点，因此可先从 QQ 尝试首条链路；最终顺序以实际可验证结果为准，网易云的 Worker 适配不推迟到产品末期。

来源探测只复用原报告指向的必要模块与固定版本，不恢复整个调研下载目录。验证 Cookie/会话、加密与请求、授权持久化、真实大小/格式、临时地址及范围读取；扫码需要用户确认时再接入真实步骤。

以已知字节音频独立验证 DAV 候选，再接入真实来源，便于分清协议问题与上游问题。检查 PROPFIND、HEAD、首/中/尾及大偏移 Range、416、取消、上游忽略 Range，以及响应中途失败；不能以“从头可播放”代替随机读取正确。

已执行 Nephele/官方 Node 桥接的限定试验，Bun 基础可用但本地 Worker 完整流失败；按原备选收敛到一套共用 Fetch 只读 DAV，复用 xmldom/range-parser。具体证据见 [ADR 0004](../docs/adr/0004-shared-fetch-readonly-dav.md)，后续围绕此路径补真实来源和客户端验收，不重复无依据的候选比较。

### 挂载路线提前探测

用同一已知音频 DAV 验证 rclone、OpenList 与播放器，提前暴露目标系统依赖和读取差异。当前执行环境可以做 HTTP/字节和构建检查；真实 Linux 挂载需具备 FUSE 的宿主，Windows 需验证所选 WinFsp 路线，macOS 需验证所选 NFS/FUSE 路线。

尽早做各系统最小挂载探测，完整启动器、安装与生命周期在 P4 完成。缺少系统环境时明确标记该端待测，继续共用代码开发；交叉编译产物不替代目标系统运行结果。

### P0 产出与转入后续阶段的条件

P0 产出应包括可复现的原型代码/命令、实际依赖版本、支持矩阵和与实现绑定的验证记录。每条记录标明宿主、插件版本/实例配置类别、操作、预期、结果和未覆盖范围，不记录秘密或私有媒体地址。

进入 P1 至少应有：最小插件可经公开合同工作；当前桌面构建与持久化可运行；一个真实来源能认证和读取音频；DAV 已知字节验证通过。Worker 免费路线、另一个来源和其他系统若仍待测，保持对应风险可见并继续验证；它们是最终范围的必需证据，不能被本地成功替代。

## P1 首条用户可用链路

目标旅程：打开 WebUI → 安装一个真实来源插件 → 创建实例并认证 → 读取一个完整内容源 → 生成默认目录 → 用现有客户端列目录、播放、向前及向后拖动 → 重启后继续使用。

只实现这条旅程所需的插件/实例管理、最小配置与认证界面、通用存储、最近成功快照和 DAV，不先打磨全部页面。优先交付一个已验证音质的真实文件，完整多音质规则随 P2 补齐。已具备挂载宿主时同时从 WebUI 完成基础挂载；尚不具备时记录其验收缺口。

P1 的可用结果必须来自真实插件、实际来源和正式请求路径，模拟登录、固定样本或独立播放器演示不能替代。完成本地首条链路后，尽快把同一旅程放到真实 Worker，区分来源行为、运行时和出口差异。

## P2 业务规则与生命周期补齐

完成网易云和 QQ 示例插件的登录持久化与刷新、自建/收藏/喜欢/发现的完整内容、顺序和重复位置，以及按实例配置的单/多音质、隐藏、向下回退、实际标签和去重。核心不因这些能力增加平台或音质专用规则。

通用核心同时补齐多实例隔离、稳定身份、文件路径冲突、完整快照切换、临时失败保留目录和取消传播；换号、配置变化、更新、移除和重装都沿真实管理入口验证。配置/认证的语义校验由插件执行，宿主负责实例版本、存储及通用输入边界。

重点检查插件代码、配置和状态版本变化：更新失败保留可用版本；移除后停止相关读取并保留引用；重装兼容插件恢复；单独删除实例后旧任务不能恢复其数据。除正常流程外，使用可控失败和交错验证这些实际责任，不为可逆的小改动编写机械测试。

## P3 完整管理体验

在 P1 已有界面上补齐目录树草稿/预览/保存、内容源选择、实例状态、刷新进度、错误与重试、插件安装与更新结果，以及本地/远程 DAV 挂载管理。使用成熟组件处理树、表单和查询状态，保留复杂交互必要的验证。

用示例插件和最小插件一起验证通用界面：无认证/音质的来源不出现这些设置；新增来源不改前端；多个实例可区分；刷新不覆盖用户布局，插件缺失和部署失败有实际可操作的状态。至此主要管理流程都应能从浏览器完成。

## P4 双宿主发行与 P5 发布验收

P4 将已经跑通的代码变成发行产品：桌面点击启动、复用后台、打开页面、随包 rclone、系统依赖检测、挂载就绪、正常卸载和退出；Windows x64、Linux x64、macOS Intel/Apple Silicon 按统一方案进行目标系统运行验证。Worker 提供初始部署模板、D1 迁移与 Secrets/部署凭据说明，插件变更自动部署并保留状态。

P5 从全新发行包或部署开始，逐项完成统一方案第 14 节的真实用户旅程和故障回归。验证 OpenList、rclone 和普通播放器的读目录/播放/拖动，记录大目录、并发读取、内存、缓存与当前免费计划资源消耗；跨版本更新时确认已有配置、布局和授权仍符合预期。

同步交付插件作者说明、公开合同、最小示例与网易云/QQ 包，说明构建、宿主兼容、配置认证、存储和读取合同；保留必要来源与第三方许可。由另一个独立插件验证不修改核心即可接入，作为扩展能力交付证据。

## 第一轮实现任务顺序

| 顺序 | 具体工作 | 可审阅产出或完成证据 |
|---|---|---|
| 1 | 建立工程与锁定初始依赖、严格类型检查、桌面/Worker 构建入口 | 源码可构建；两端导入边界清楚，Vite 只维护一套 WebUI 构建 |
| 2 | 实现试验版插件清单/合同和最小来源包 | 插件不依赖核心内部模块，无账号/歌单/音质也能提供目录与文件 |
| 3 | 编译桌面核心并加载外置最小插件，保存两个实例 | 运行编译产物，修改和重启后状态保留，实例不串数据 |
| 4 | 有针对性复核 Worker 部署接口，用同一最小插件做普通免费路线 PoC | 实际部署结果、绑定与状态保留、失败恢复和代码版本对应关系；若外部条件未就绪则记录明确待测项 |
| 5 | 以已知音频确定 DAV 接线及范围读取方案 | PROPFIND、HEAD、206/416、取消和真实字节正确，可被现有客户端读取 |
| 6 | 接入第一个真实示例插件的最小认证/内容/取流，并探测另一个来源的 Worker 风险点 | 真账号流程与真实完整音频证据，核心没有平台特例 |
| 7 | 用最小 WebUI 串联安装、实例认证、默认目录和播放，验证重启 | 得到 P1 首条可重复的真实用户旅程 |
| 8 | 在可用宿主接入 rclone/OpenList，完成挂载探测；归纳 P0 结果 | 支持矩阵、已知障碍与接下来的具体实现任务 |

表中为优先顺序，独立步骤可交错推进；例如等待真实 Worker 或扫码时先完成固定字节协议验证，不等待外部条件才开始全部开发。第一轮结束依据产出收口，不承诺未经验证的固定天数。

## 需求覆盖与后续决策

| 需求 | 首次接线 | 最终收口 |
|---|---|---|
| FR01、FR02、FR06、FR07、FR09、FR13、FR14 | P0/P1 基础认证、真实内容、读取协议、状态与凭据隔离 | P2 失败/并发边界，P5 真实双宿主和客户端 |
| FR03—FR05、FR08、FR18 | P2 两个示例插件的完整来源与音质规则 | P5 两宿主真实账号与内容验证 |
| FR19—FR24 | P0 最小插件、合同与多实例；P1 管理入口 | P2 生命周期，P3 通用界面，P5 独立插件验收 |
| FR25 | P0 普通 Worker 模块组装与自动部署探测 | P4 产品化，P5 从部署模板及升级场景验证 |
| FR10—FR12 | P0 目标宿主挂载探测，P1 具备条件时串联 | P3 管理入口，P4/P5 三端及远程 DAV |
| FR15、FR17 | P1 基础状态与默认目录 | P2 身份与快照，P3 目录编辑与诊断，P5 刷新/恢复回归 |
| FR16 | P0 固定实际依赖及来源信息 | P4 产物与模板，P5 使用/插件文档及许可 |

具体 API 形状、包格式、DAV 候选、SQL 和 UI 接线由工程设计处理。只有验证结果确实要求改变已确认范围或部署前提，例如必须付费、增加外部服务、无法提供完整音频，或更新带来明显使用中断，才携带证据回到产品讨论。

旧工作量估算未计插件化增量。P0 后根据真实适配工作和外部环境可用性重估剩余投入，P1 后再按真实实现进度调整。进度按可用旅程、验收证据和剩余障碍报告，不按文档数量、代码量或“构建成功”认定交付。

## 计划维护

[统一方案](musicfs-requirements-and-technical-design.md)保存需求与验收，本计划保存执行顺序，[Codex 目标](../docs/codex-goal.md)保存持续执行要求，[验收台账](../docs/verification.md)保存实现状态与证据；ADR 保存有取舍的架构决定。进入实现后，将真实验证命令、版本和结果与对应代码一起维护，并更新本计划的当前状态。新增发现优先修改现有责任文档，不复制整套方案或扩展为额外管理系统。
