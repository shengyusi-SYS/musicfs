# 整体思路、工作量、风险与投入产出评估

日期：2026-10-18  
依据：[当前统一需求与技术方案](musicfs-requirements-and-technical-design.md)  
性质：开发预算与优先级判断，不是实测结果或交付承诺。

2026-10-20 范围更新：插件 Q1—Q11 已确认，新增可安装插件、声明式配置认证、多实例隔离及 Worker 自动部署，音质业务移入示例插件。下列数值为原 18 项固定平台范围的历史预算，尚未计入这些增量，不能作为新方案的完整总预算；在 P0 明确加载、部署与适配量后重新估算，不机械加减一个插件化百分比。当前领域职责以 [统一方案](musicfs-requirements-and-technical-design.md) 为准。

后续已完成 [依赖复用与方案精简核查](musicfs-simplification-and-dependencies.md)。本估算原已假设复用平台 API 与部分 UI；不能再次按同一收益统一打折。具体 DAV 库和双端集成通过 P0 后，再按实际适配量更新预算。

桌面进一步建议采用 [Bun 可执行程序与内置能力](musicfs-bun-desktop-evaluation.md)。其收益集中在运行时合包、HTTP、SQLite 与后端构建配置，前端继续使用 React + Vite，不计入替换前端工具的收益。原表保留为预算参考，待 Bun 编译产物与三端运行验证后更新桌面发行项，不据此给整体工期统一打折。

## 1 总体判断

方案成立的关键是：让音乐平台的数据成为可读取的文件视图，再通过成熟协议和挂载工具接入已有播放器。核心价值集中在登录后内容读取、可靠音频访问，以及 WebDAV 带来的生态兼容。

这属于中等规模的工具项目。已有 API 实现、WebDAV 和 rclone 显著减少需要自研的部分；剩余主要成本是双平台适配、双宿主运行差异、音频读取正确性和三端发行。拖拽树和多音质是边界明确的增量功能。

目前只有方案与源码核查，尚无本项目的完整链路实测。投入判断的置信度最高的是页面与普通业务逻辑，最低的是网易云 Worker 移植、CF 出口下的平台行为及最终三端兼容。

## 2 整体思路

```text
网易云 / QQ：登录、歌单、推荐、歌曲、音质与播放地址
                         ↓
示例插件：来源认证、内容与音质规则 → 共用核心：实例、布局、快照与协议
                         ↓
                  只读 WebDAV
                   ↙          ↘
           OpenList / 播放器   桌面内置 rclone → 盘符或目录
```

WebUI 管理这套核心：扫码、设置、拖拽布局和状态。目录树保存用户安排，平台刷新更新其内容。单版本输出一个音质，多版本输出多个实际音频；音质缺失时按设置隐藏或回退，无完整播放权限时隐藏。

桌面建议使用可点击的 Bun 编译程序启动本地后台，内嵌 WebUI，提供页面与 DAV，并管理随包 rclone。Worker 同时提供静态 WebUI、管理 API 和 DAV，保存云端账号、设置与元数据，不提供本机挂载。两种部署共用代码，独立运行。

## 3 估算口径

- 一名熟悉 TS、HTTP 和常见前端组件的开发者，正常使用 AI 辅助；一人日约 6—8 小时有效工作。
- 复用既有平台协议和扫码实现，采用成熟组件完成基础 WebUI 与拖拽树。
- 有可用的账号及三端测试环境；排期不计等待测试设备或用户扫码的时间。
- 本历史估算范围为原 18 项需求；插件化后已扩展为统一方案中的新范围，原估算未计增量。
- 每个模块包含其自身验证；最终验收项用于跨模块、客户端和发行包联调，避免把同一次测试重复计算。
- P0 的结果可以继续使用；后续平台接入预算为其剩余产品化工作。若发现必须重新逆向核心协议或 CF 出口无法使用，需重新评估，不能把这种情况强行包含在上限内。

以下数字都是工程判断，不来自速度基准或历史实测。

## 4 分项工作量与 ROI

这里的 ROI 指用户收益、代码复用和减少后续维护相对于开发投入的价值，不是收入预测。基础能力标为高 ROI，意味着它使其他能力有用，并不代表可以独立省略或替代。

| 工作项 | 人日估算 | 实现风险 | 投入产出判断 |
|---|---:|---|---|
| P0：平台、Worker、音频与三端挂载验证 | 3—5 | 高 | 极高；最早发现会改变整个方案的事实，减少后续返工 |
| 网易云接入，含必要 Worker 移植 | 4—8 | 高 | 高；覆盖核心平台，Worker 移植带来额外验证与维护 |
| QQ 接入，含分类、分页与会话 | 2—4 | 中高 | 高；已有 serverless 入口可复用，仍需真实账号验证 |
| 内容源、完整目录、命名与刷新 | 3—5 | 中 | 高；所有入口共用，决定内容能否正确呈现 |
| 音频流、真实元数据与只读 WebDAV | 5—8 | 中高 | 极高；直接决定能否播放、拖动及接入现有生态 |
| 账号、设置、布局与双端持久化 | 2—4 | 中 | 高；让登录和配置可以稳定使用 |
| 基础 WebUI：扫码、设置、状态 | 3—5 | 低中 | 高；降低操作门槛，一套页面覆盖本地与云端 |

| 桌面启动器、rclone 生命周期与三端打包 | 5—9 | 中高 | 高；把开发者可运行版本变成用户可直接安装使用的工具 |

| **基准合计** | **36—63** | — | — |

网易云行已经包含平台层的 Worker 兼容工作；Worker 产品化行只计宿主、部署与绑定，不能再次计算相同移植。OpenList 配置与联调约 0.5—1 人日，已包含在 DAV 与最终联调中，不额外相加。OpenList 现有驱动默认支持代理方式，无需编写专用驱动。[OpenList 文档](https://doc.oplist.org/guide/drivers/webdav)

预算建议留约 25% 调整余量，按 **45—80 人日** 规划。一人全职约 **9—16 周**。这是覆盖当前范围并完成三端发布的估算，不是完成一次演示所需时间。

可以在累计约 **10—15 人日** 时争取交付第一个可用切片：一个已验证平台、基础 WebUI 登录、默认目录、单音质、DAV 播放与开发环境挂载。它用于验证实际收益，不代替最终的双平台、Worker、三端发行与目录定制范围。

AI 对页面、类型、适配代码和常规验证有帮助；实际账号登录、上游行为、三端安装与播放器兼容仍需运行验证，因此不使用统一“提速倍数”推算交付时间。

## 5 实际风险及处理顺序

| 风险 | 依据与影响 | 最划算的处理 |
|---|---|---|
| 上游接口与会话变化 | 本项目依赖非官方协议实现；接口、凭据交换或有效期处理变化会直接影响登录和播放 | 内嵌必要接口，锁定版本与小范围补丁；保留登录、分页、取流的回归样本 |
| 网易云 Worker 兼容及 CF 出口 | 原网易云入口存在文件扫描、文件状态与 Node Agent；QQ 已有 serverless 入口，但其源码也记录运行环境差异。代码移植与出口行为是两项独立问题 | P0 在真实 Worker 跑通扫码、账号内容、完整音频与范围读取，先给出通过或具体失败原因 |
| 看似能播放，随机读取却错误 | 音频临时地址、大小、编码、Range 与客户端缓存共同影响拖动和再次打开 | 用已知音频校验首尾与大偏移字节，同时用 OpenList、rclone、播放器实播 |
| 三端挂载和发行差异 | rclone 已实现挂载，但 Windows 仍需 WinFsp，其他系统的依赖、权限和卸载机制不同 | 共用挂载管理流程，宿主差异集中处理；每个系统从发行包开始验证 |
| 大歌单乘以多个音质 | 若逐曲逐档解析，调用量约为曲目数乘以音质数；目录项与索引工作也相应增长 | 优先平台元数据、缓存及必要时解析，限定并发；不在每次列目录前重复解析所有版本 |
| 拖拽改变已访问路径 | 组织自由度意味着路径可能变化，播放器和 OpenList 可能保留旧目录 | 内部身份稳定，布局与内容分开，明确保存后的目录刷新行为 |

这些是当前链路直接产生的风险，不需要为此新增复杂权限系统或其他产品能力。网易云适配依据见固定提交的 [入口](https://github.com/NeteaseCloudMusicApiEnhanced/api-enhanced/blob/19c7dad6db7d660954c7a615a686ff0acb030f91/main.js)、[请求实现](https://github.com/NeteaseCloudMusicApiEnhanced/api-enhanced/blob/19c7dad6db7d660954c7a615a686ff0acb030f91/util/request.js)；QQ 依据见其 [serverless 实现](https://github.com/yakult-green-tea/qq-music-api/blob/e7dff2e1e2496780702bda528362edbdaf6bbf6e/src/serverless/index.ts)。Windows 依赖见 [rclone 文档](https://rclone.org/commands/rclone_mount/)。

## 6 哪些选择最值得保留

**WebDAV 接 OpenList、rclone 负责挂载，ROI 最高。** 一份目录和读取实现覆盖多个客户端，且不用承担系统文件驱动的开发。OpenList 接入是协议兼容工作，主要成本在 DAV 的正确实现，不在 OpenList 本身。

**共用 TS 核心与 WebUI，ROI 高。** 平台数据、音质与目录规则只实现一套，宿主差异集中在存储、监听和挂载。仍需分别验证 Bun 与 Worker，代码复用不能替代运行环境测试。

**Bun 收拢桌面基础能力，ROI 高。** 能减少随包运行时、静态资源和原生 SQLite 绑定的维护；rclone 生命周期、平台接口与系统挂载验证仍需完成。具体节省量以编译和运行结果更新，不另设未经验证的提速倍数。

**内嵌 API，安装体验收益高，维护成本持续存在。** 用户少部署两个服务，项目则需要跟进上游补丁并随发行包或 Worker 更新。这是当前方案中最需要长期投入的部分。

**WebUI 替代 CLI，用户收益高，总开发量未必更少。** 登录、配置与挂载后台仍然存在，另外需要页面；收益来自无需记命令和方便查看状态。共用浏览器页面控制了双端界面成本。

**Worker 的收益依赖使用场景。** 对没有 NAS 或常驻电脑的用户价值高；已有常驻设备时，收益主要是部署位置和可达性选择。它仍属于已确定范围，但应先验证平台可用性，再投入部署体验完善。

**目录拖拽与多音质提供差异化，但应建立在稳定读取之后。** 两项合计约 4—7 人日，可控，适合后续增量完成；不应先投入大量界面打磨再发现核心音频链路不可用。

## 7 运行与维护成本

对自用、小请求规模场景，预计主要投入在人力与兼容维护。具体云端费用取决于实际请求、CPU 与 D1 用量，不能只根据歌曲数量推算。

当前 Workers 付费计划最低为 5 美元/月，官方计费页说明不另收数据传输和带宽费用；这不代表整个应用始终只需该费用。免费计划有每次调用 10 ms CPU 等限制，音频转发等待网络与协议加密、XML 生成的 CPU 消耗需分别测量，不能未经测试承诺免费计划稳定运行。[Workers 定价](https://developers.cloudflare.com/workers/platform/pricing/)、[运行限额](https://developers.cloudflare.com/workers/platform/limits/)

桌面缓存按实际读取音频增长；多版本不必预先下载全部版本。平台账号原有权益不因本项目发生改变。

持续维护主要是平台协议与会话、依赖升级、客户端兼容。现阶段没有故障频率资料，不虚构固定的“每月维护几天”；先用试用期的实际更新与故障记录建立预算。外部协议出现重大变化时，恢复周期可能超出正常开发估算。

没有用户规模、使用频率或收入资料，因此不能计算可信的货币 ROI、回本时间或收益百分比。若只为一次性自用，完整产品化投入偏大；若要长期使用并作为三端开源工具发布，安装便利与生态复用更能摊薄投入。

## 8 建议推进顺序

1. **先用 3—5 人日验证方案成立。** 验证两平台在本地与 CF 的登录和音频链路，并完成三端挂载样本；首要结论是已测通过范围及明确阻碍。
2. **尽早交付一条可用链路。** 从一个通过验证的平台开始，让 WebUI 登录、默认目录、单音质、DAV 和现有客户端真正工作，直接判断日常使用价值。
3. **补齐第二平台与双宿主能力。** 完成持久化、刷新、异常处理与 OpenList 联调，把主要规则留在共用核心。
4. **加入拖拽与多音质体验。** 保持布局与内容独立，验证回退与文件去重，随后完善三端发行与 Worker 部署。

这是实现与验证顺序，不改变已确认的最终范围。初期最值得投入的是消除平台与运行环境不确定性，其次是稳定音频和协议兼容；界面组织体验随后兑现。
