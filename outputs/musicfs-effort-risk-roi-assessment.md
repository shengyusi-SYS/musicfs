# MusicFS 方案复盘与工作量口径

上一轮性能实现已交付 Windows dev.11，具体范围见[发行页](../docs/release.md)；本轮跨领域复评发现的局部优化候选及投入见[场景复评](musicfs-performance-review.md)。本页保留整体判断和估算口径，候选及下一步只有[实施计划](musicfs-implementation-plan.md)一个入口；近期可复用结论集中在[工程经验](../docs/engineering-lessons.md)。

## 方案是否需要调整

保留 `extensions` 管安装、`sources` 管实例与认证、`library` 管快照/布局/文件的分工。没有依据要求重新划分整个领域或增加通用 Service/Manager、队列、ORM 和缓存平台。

近期有效调整集中在工作发生的时机与所有权：先发布可用清单、按文件准备最终表示，复用准确描述和 SDK 真批量；目录、资料和已读字节分别缓存，桌面复用已有 rclone，Worker 保持适合自身预算的流式路径。这些是原模块内的减法和适配，不是另建一套系统。

## 问题的共同原因

| 共因 | 后续决策原则 |
|---|---|
| 模块或探针成功被扩大为整个使用旅程通过 | 区分机制、实际宿主、消费者与最终发行物的证据；先覆盖用户入口 |
| 缓存名称笼统，配置与实际运行混淆 | 指明对象、身份、存储、失效及占用；实测原生模式与持久复用 |
| 小 Range 的失败被扩大成所有方案不值得 | 按具体请求形态判断，比较现有原生能力与最小垂直样本 |
| 追求统一或“全部完成”不断衍生工作 | 统一合同，允许宿主差异；每个新增任务说明用户收益与停止条件 |
| 阶段进展反复追加到设计和计划 | 当前说明重写，历史进入版本证据；经验只保存长期结论 |

## 剩余工作量

本轮任务以评估为范围，新候选尚未实施；优先级、投入和最小验证只在[复评报告](musicfs-performance-review.md)维护，**不沿用旧 P4/P5 的剩余人日估算**。原生系统、真实全库 GUI 耗时、免费 Worker 资源或自然续期的未验范围仍见[台账](../docs/verification.md#当前有限剩余清单)，不会因本次文档整理变成通过或重新成为必做矩阵。

出现新反馈时，先估定位样本，再估实现、受影响验证和交付；把有效开发时间与账号协作/VM 等待分开。互斥方案不相加，已完成路径不重复计费，代理数量不直接折算工期。没有新证据前不为潜在缓存引擎、额外云存储或理论反例预留开发预算。
